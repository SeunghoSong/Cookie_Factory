# POC 제작 계획표: 주머니 속의 스마트 팩토리

**프로젝트명**: SAM 2 및 모바일 스트리밍 기반 실시간 불량 과자 검출 시스템
**개발 기간**: 5시간 (11:00 ~ 16:00) / **인원**: 2명

> ⚠️ **변경 이력**: 초기 기획(SAM 2 딥러닝 기반) 대비 실제 구현 과정에서 아래 3건이 실전 판단으로 변경됨. 상세 사유는 "0. 실제 구현 변경 사항" 참조.

---

## 0. 실제 구현 변경 사항 (Pivot Log)

개발 도중 CPU-only Docker 환경에서 SAM 2 추론 속도가 목표(실시간 30fps)를 크게 벗어나는 것을 조기에 발견하여, 아래와 같이 아키텍처를 조정함. 변경 후에도 판정 로직의 입력/출력 스키마 골격(원형도 기반 판정)은 유지되어 다른 컨테이너와의 인터페이스 충돌은 없었음.

| # | 원래 기획 | 실제 구현 | 변경 사유 | 결과 |
|---|---|---|---|---|
| 1 | C3: SAM 2 딥러닝 기반 픽셀 단위 마스크 추출 | **OpenCV 기반 초경량 기하학 수학 엔진**으로 대체 | CPU 환경에서 SAM 2 추론 시 프레임당 약 3초 소요 → "실시간 스트리밍" 목표 자체가 성립 불가능함을 조기 발견 | 프레임당 처리 시간 **약 15ms**로 단축. 부가적으로 결함 유형 4종(HALF/CUT/WEDGE/BITE) 세부 분류까지 확장 구현 |
| 2 | C2: 단순 이진화(threshold) 후 bounding box 좌표만 전달 | **6단계 전처리 파이프라인** 구축 (가우시안 블러 → CLAHE 조명 보정 → 모폴로지 연산 → 면적/비율 노이즈 컷 → 3라인 슬라이싱) | 실제 촬영 시 모니터/화면 촬영 환경에서 모아레(픽셀 격자 무늬)와 조명 반사로 인해 마스크가 찢어지는 현상 발견 | C3로 전달되는 데이터의 노이즈를 원천 차단, 판정 정확도 저하 방지 |
| 3 | C3: Nginx 기반 다중 Replica 로드밸런싱(Scale-out) | **단일 서버 구조 유지** (Scale-out 미적용) | 1번 변경으로 프레임당 처리 시간이 15ms 수준까지 단축되어, 단일 인스턴스만으로 초당 60프레임 이상 처리 가능함을 확인 → 별도 확장 불필요 | 인프라 복잡도 및 서버 비용 절감 (Nginx 로드밸런서, 추가 컨테이너 불필요) |

> **주의**: 위 변경은 "판정 방식"과 "인프라 확장 전략"에 대한 변경이며, 4단 마이크로서비스(C1~C4) 구조 자체와 각 컨테이너의 역할 분담(수집/전처리/판정/시각화)은 원래 기획과 동일하게 유지됨. 아래 본문은 변경 사항을 전부 반영한 최신 버전임.

## 2. 사전 인터페이스 협의 사항 (Kick-off, 11:00~11:20 필수)

착수 전 두 담당자가 반드시 아래 스펙에 합의해야 함 (합의 없이 병렬 개발 시 통합 실패 위험).

| # | 인터페이스 | 담당 경계 | 협의 필요 항목 |
|---|---|---|---|
| 1 | C1 → C2 프레임 전달 | 수집팀 → 판정팀 | 전송 프로토콜(WebSocket/HTTP), 프레임 포맷(Base64 JPEG vs Raw Bytes), 프레임 크기/해상도, 전송 주기(fps) |
| 2 | C2 → C3 전처리 데이터 | 판정팀 내부 | 6단계 전처리 결과 포맷, 메타데이터(frame_id, timestamp) 포함 여부, **정제된 객체 영역(contour_region) 좌표 스펙**(아래 2-1 참조) |
| 3 | C3 → C4 판정 결과 | 판정팀 → 수집팀 | 판정 결과 스키마(JSON): `{frame_id, is_defective, defect_type, circularity, mask_polygon, bbox}` |
| 4 | C4 → C1 역전송 | 수집팀 내부 | 마킹된 프레임 재전송 방식, 원본 프레임과의 매칭 키(frame_id) |
| 5 | 공통 | 전체 | 원형도 임계값(threshold) 초기값 합의 (예: 0.75 미만 = 불량), 결함 유형별 세부 판정 기준, 에러/타임아웃 처리 방식 |
| 6 | 공통 | 전체 | 포트 번호 및 네트워크 구성(Docker network 이름, ngrok 포워딩 대상 포트) |

### 2-1. C2→C3 판정 파이프라인 전략 (필수 확정 사항) — **[변경됨: SAM 2 → OpenCV 기하학 엔진]**

> 기존에는 C2가 컨투어를 찾아 SAM 2용 box prompt를 생성하는 구조였으나, C3가 딥러닝 대신 기하학 수학 엔진으로 대체되면서 C2의 역할이 **"판정 가능한 수준으로 노이즈를 제거한 정밀 객체 영역/마스크를 직접 만들어 넘기는 것"**으로 확장됨.

| 항목 | 결정 사항 |
|---|---|
| C2 전처리 방식 | **6단계 노이즈 차단 파이프라인**: ① 가우시안 블러(고주파 노이즈 제거) → ② CLAHE 조명 보정(반사/음영 보정) → ③ 모폴로지 연산(구멍 메우기, 마스크 끊김 복원) → ④ 면적/비율 기반 노이즈 컷(비정상적으로 작거나 형태 비율이 어긋난 컨투어 제거) → ⑤ 3라인 슬라이싱(관심 영역을 3분할하여 처리 안정성 확보) |
| C3 판정 방식 | **OpenCV 기하학 수학 엔진**: 딥러닝 모델 없이 컨투어의 Area/Perimeter 기반 원형도(Circularity) 계산 + 형태학적 특징(둘레 굴곡, 결손 위치/각도 등)으로 결함 유형 분류 |
| 전제 조건 | 프레임당 검출 대상 과자 1개 등장 가정 (다중 객체 시 최대/중심 컨투어만 선택) |
| C2 → C3 전달 데이터 | `{frame_id, timestamp, contour_points, bbox, cleaned_mask}` (SAM2용 box_prompt 대신, 6단계 전처리로 정제된 컨투어/마스크 직접 전달) |
| C3 처리 | 정제된 컨투어로 Area/Perimeter 계산 → Circularity = 4π×Area/Perimeter² → 임계값 판정 → 결함 형태 특징 분석으로 **HALF/CUT/WEDGE/BITE** 4종 분류 |
| 결함 유형 정의(예시) | HALF: 반으로 쪼개짐 / CUT: 일부 절단 / WEDGE: 쐐기형 결손 / BITE: 베어문 형태 결손 (※ 정확한 분류 기준은 Kick-off 시 캘리브레이션 샘플로 확정) |
| 실패 예외 처리 | 컨투어 미검출(빈 프레임/배경만 존재) 시 C2가 `contour_points: null` 전달 → C3는 판정 스킵 후 "No Object" 상태로 C1 통보 |

> **리스크(해소됨)**: 기존 "배경-객체 대비 부족 시 컨투어 탐지 실패" 리스크는 6단계 전처리(CLAHE+모폴로지)로 상당 부분 완화됨. 다만 모아레·반사가 극심한 환경에서는 여전히 사전 캘리브레이션 필요.

> **권장**: JSON 스키마와 포트 정의는 11:20까지 공유 문서(또는 슬랙 핀)에 고정하고, 이후 변경 시 즉시 상대방에게 통보.

## 3. 데이터 파이프라인 세션

전체 흐름을 한 화면에서 검증할 수 있도록, 각 구간의 입력/처리/출력/전송 방식을 하나의 테이블로 통합 정리한다.

### 3-1. End-to-End 데이터 흐름

| 구간 | 입력(Input) | 처리(Processing) | 출력(Output) | 전송 방식 | 예상 지연 요인 |
|---|---|---|---|---|---|
| 스마트폰 → C1 | 카메라 원본 프레임(RGB) | 브라우저 캡처 후 JPEG 인코딩(Base64 or Binary) | `{frame_id, timestamp, image_data}` | WebSocket (30fps 목표) | 인코딩 비용, 모바일 네트워크 대역폭 |
| C1 → C2 | 위 프레임 메시지 | 별도 변환 없이 릴레이(Gateway 역할) | 동일 스키마 | 내부 WebSocket/HTTP(Docker network) | Gateway 큐잉 지연 |
| C2 → C3 | `{frame_id, timestamp, image}` | **6단계 전처리**(블러→CLAHE→모폴로지→노이즈컷→3라인 슬라이싱)로 정제된 컨투어/마스크 산출 | `{frame_id, timestamp, contour_points, bbox, cleaned_mask}` | 내부 HTTP/gRPC(Docker network) | 전처리 6단계 누적 연산 시간 (단, ms 단위로 경미) |
| C3 → C4 | `{frame_id, contour_points, cleaned_mask}` | **OpenCV 기하학 엔진**: Area/Perimeter → 원형도 계산 → Pass/Fail 판정 → 결함 유형(HALF/CUT/WEDGE/BITE) 세부 분류 | `{frame_id, is_defective, defect_type, circularity, mask_polygon, bbox}` | 내부 HTTP/gRPC(Docker network) | **약 15ms/frame** (딥러닝 대비 병목 아님, 단일 서버로 충분) |
| C4 → C1 | 판정 결과 + 원본 이미지 | 원본 프레임에 마스크/bbox + 결함 유형 라벨 오버레이 마킹 | 마킹된 이미지(JPEG) + 판정 라벨 | 내부 HTTP/WebSocket(Docker network) | 이미지 합성/인코딩 비용 |
| C1 → 스마트폰(화면) | 마킹된 프레임 | 프론트엔드 렌더링 | 화면 표출(Pass/Fail + 결함 유형 오버레이) | WebSocket | 렌더링 프레임 드랍 |

### 3-2. 공통 데이터 스키마 (frame_id 기준 전 구간 추적)

| 필드 | 타입 | 설명 | 최초 생성 구간 |
|---|---|---|---|
| `frame_id` | string/int | 프레임 고유 식별자(단조 증가 또는 UUID) | C1 (스트리밍 수신 시점) |
| `timestamp` | ISO8601 / epoch | 프레임 캡처 시각 | C1 |
| `image` | Base64 string / binary | 원본 또는 처리 중 이미지 데이터 | 스마트폰(C1 수신) |
| `contour_points` | 좌표 배열 or `null` | 6단계 전처리로 정제된 객체 컨투어 좌표 | C2 |
| `bbox` | `[x_min, y_min, x_max, y_max]` | 컨투어의 바운딩 박스 | C2 (C3에서 재계산 가능) |
| `cleaned_mask` | 이진 마스크 or 폴리곤 | 노이즈 제거 완료된 마스크 | C2 |
| `mask_polygon` | 좌표 배열 | 최종 판정에 사용된 마스크 폴리곤 | C3 |
| `circularity` | float (0~1) | `4πA/P²` 계산 결과 | C3 |
| `is_defective` | boolean | 임계값 기준 Pass/Fail 판정 | C3 |
| `defect_type` | enum (`HALF`/`CUT`/`WEDGE`/`BITE`/`null`) | 결함 세부 유형 (정상일 경우 null) | C3 |

> **원칙**: `frame_id`는 C1에서 생성된 후 전 구간(C2→C3→C4→C1)에서 그대로 유지되어야 한다. 이 값이 유실/변조되면 C4의 역전송 매칭(원본 프레임 ↔ 판정 결과)이 깨지므로, 각 컨테이너는 응답 시 반드시 수신한 `frame_id`를 그대로 반환한다.

### 3-3. 처리량 확보 전략 — **[변경됨: Scale-out 불필요, 단일 서버 구조]**

| 항목 | 내용 |
|---|---|
| 원래 계획 | C3(SAM 2)만 다중 복제 + Nginx 라운드로빈 분산 (Scale-out) |
| **변경 후** | C3가 OpenCV 기하학 엔진(약 15ms/frame)으로 대체되어 **단일 인스턴스로 초당 60프레임 이상 처리 가능** → Scale-out 불필요 |
| 근거 | 딥러닝 추론(GPU 의존, 초 단위 연산) 대신 CPU 기반 경량 수학 연산(Area/Perimeter/형태 분석)만 수행하므로 컨테이너 1개로 충분한 여유 처리량 확보 |
